# Техническое задание для сборки данных диаграмм (приложения А, Б, В, Г)

**Объект:** модуль «Планирование перерабатывающих процессов» (Долгов Е.В.)  
**Диплом:** «Программный комплекс по учёту и переработке промышленных отходов»  
**Архитектура:** тонкий клиент `planning-module` + общий REST API `/api/v1/*` платформы `waste-complex-platform`  
**СУБД:** PostgreSQL 16, БД `waste_complex`

Источники в репозитории: `planning-module/frontend/`, `waste-complex-platform/api/app/routers/planning.py`, `services/planner.py`, `docs/структура_БД.txt`.

> **Важно:** в черновиках `uml-components.puml` указаны SSE и Celery/Redis — в прототипе **не используются**. Ниже — фактическое поведение кода.

## Блок 1. Модели бизнес-процессов (BPMN, Draw.io / Mermaid)

### 1.1. Роли и пулы (Pools & Lanes)

| Pool (пул) | Lane (дорожка) | Роль в дипломе | Системный актор |
|------------|----------------|----------------|-----------------|
| **Учёт поступления** | Кладовщик / модуль учёта | Регистрация партии | `waste-complex-platform` → accounting |
| **Планирование** | **Диспетчер** | Построение и утверждение сменного плана | UI `planning-module` (кнопки «Новый план», «Утвердить») |
| **Планирование** | **Модуль автоматического планирования (бэкенд)** | Расчёт приоритетов, расписания, KPI, уведомлений | `services/planner.py`, `services/kpi.py`, `services/notifications.py` |
| **Планирование** | **Главный технолог / руководитель** *(концептуально)* | Утверждение плана для производства | В прототипе — тот же диспетчер (`POST /plans/{id}/approve`) |
| **Производство** | **Производственная линия L1/L2** | Исполнение операций по плану | Мониторинг (`batch_stage_progress`) |
| **Производство** | **Оператор смены** | Фиксация событий, отклонений | Модуль мониторинга (мобильный клиент) |
| **Внешние системы** *(опционально)* | MES / SCADA / ERP | События простоя, фактические данные | Не реализовано в прототипе (заглушка в UML) |

**Рекомендуемая BPMN:** 3 основных пула — **Учёт → Планирование (диспетчер + бэкенд) → Производство**.

### 1.2. Основной бизнес-процесс (счастливый путь)

**Триггер:** партия зарегистрирована в учёте (`waste_batches`, статус `accepted` / `queued`).

| Шаг | Кто | Действие | API / автоматика |
|-----|-----|----------|------------------|
| 1 | Модуль учёта | Создание партии: код, ФККО, класс опасности, объём, срок хранения, маршрут `route_codes` (напр. `L1,L2`) | `POST /api/v1/accounting/batches` |
| 2 | Бэкенд | Расчёт **приоритета** партии (класс опасности + срочность хранения + экономика) | `compute_priority()` при `GET /batches` |
| 3 | Диспетчер | Открывает модуль, вкладка «Партии» — просмотр очереди, рисков хранения | `GET /api/v1/batches` |
| 4 | Диспетчер | **Клик:** «Новый план» — задать имя и горизонт (по умолчанию 8 ч) | `POST /api/v1/plans/build` |
| 5 | Бэкенд | Архивация старых черновиков; жадное построение `schedule_items` по маршруту и мощностям линий; статус плана `draft` | `build_schedule()` |
| 6 | Бэкенд | Проверка триггеров **T1** (разрывы > 0,5 ч на линии), **T2** (хранение < 6 ч) | `check_and_create_notifications()` |
| 7 | Диспетчер | Просмотр Gantt и таблицы операций, KPI на «Обзоре» | `GET /plans`, `GET /dashboard/kpi` |
| 8 | Диспетчер | **Клик:** «Утвердить план» | `POST /api/v1/plans/{id}/approve` |
| 9 | Бэкенд | Старые `approved` → `archived`; синхронизация плановых дат в мониторинг | `sync_stages_from_plan()` |
| 10 | Производство | Исполнение смены по утверждённому плану, обновление статусов этапов | `PATCH /monitoring/batches/{id}/stages/{id}` |

**Автоматически (без клика):** шаги 2, 5, 6, 9.  
**Требуется клик пользователя:** 4, 8 (+ опционально симуляция/перепланирование).

**Формула приоритета** (`compute_priority`):

- вес класса опасности: `(6 - hazard_class) * 25`;
- срочность хранения: до 40 баллов при остатке < 48 ч;
- экономика: до 15 баллов от `economic_value`.

### 1.3. Обработка исключений и сбоев

#### Авария / поломка на линии

| Этап | Поведение |
|------|-----------|
| Фиксация | В мониторинге: `POST .../events` с `event_type: emergency_stop` |
| Планирование | Диспетчер: **«Перепланировать · простой L2 (8 ч)»** → новый черновик с сдвигом `line_free_at` для L2 | `POST /plans/{id}/replan` |
| Симуляция | Сценарий **«Аварийный»**: `line_downtime: {L2: 8}` без утверждения | `POST /simulations` (`scenario: emergency`) |
| Уведомления | T1 — прогноз простоя между операциями в плане |

#### Приоритетная партия задерживается в поставке

| Этап | Поведение |
|------|-----------|
| Данные | Партия не в очереди (`status` не `accepted`/`queued`) — **не попадает** в `build_schedule` |
| Риск | Если партия в БД, но срок хранения истекает — **T2**, KPI «Риск хранения» |
| Пересчёт | Диспетчер строит новый план — приоритет пересчитывается по `received_at` и `storage_deadline_hours` |

#### Конфликт по мощностям / не влезает в горизонт

| Этап | Поведение |
|------|-----------|
| Алгоритм | Операции с `start >= horizon_end` **пропускаются** (не создаётся `schedule_item`) |
| Конфликт в UI | Нет отдельного шлюза «конфликт» — диспетчер видит неполное расписание, низкий `% выполнения плана`, T1/T2 |
| Разрешение | Симуляция **ускоренного** горизонта (−15%) или **перепланирование**; ручного редактирования полос Gantt **нет** |

### 1.4. Входящие и исходящие документы / сущности

| Документ / сущность | Откуда | Куда | Формат |
|---------------------|--------|------|--------|
| Заявка / карточка партии | Учёт | Планирование | `waste_batches` |
| Очередь с приоритетами | Бэкенд | Диспетчер | JSON `BatchOut[]` |
| **Черновик расписания** | Бэкенд | Диспетчер | `schedule_plans` + `schedule_items`, status `draft` |
| **Утверждённый сменный план** | Диспетчер → бэкенд | Мониторинг | status `approved`, `approved_at` |
| Отчёт загрузки / KPI | Бэкенд | Дашборд | `KpiDashboard` |
| Сценарий «что если» | Симуляция | Сравнение KPI | `SimulationCompare` |
| Оповещение T1/T2 | Бэкенд | Центр уведомлений | `notifications` |
| Версия плана (история) | Бэкенд | PlanPicker | `version_no`, `parent_plan_id` |

**Жизненный цикл плана:** `draft` → `approved` → `archived` (при утверждении новой версии). Симуляции: `is_simulation = true`, утверждению не подлежат.

### 2.4. DFD (приложение Б, уровни 0–1)

**Контекст (уровень 0):**  
Внешние сущности: **Модуль учёта**, **Диспетчер**, **Мониторинг**, **PostgreSQL**.

**Уровень 1 — процессы:**

| № | Процесс | Вход | Выход | Хранилище |
|---|---------|------|-------|-----------|
| P1 | Приём данных партий | Партия из учёта | Очередь партий | D1 `waste_batches` |
| P2 | Расчёт приоритетов | D1, текущее время | priority_score | D1 |
| P3 | Построение расписания | D1, D2 `production_lines`, D3 `routing_operations`, параметры смены | Черновик плана | D4 `schedule_plans`, D5 `schedule_items` |
| P4 | Контроль рисков | D4, D5, D1 | Уведомления T1/T2 | D6 `notifications` |
| P5 | Расчёт KPI | D5, D4 | OEE, загрузка линий | — (ответ API) |
| P6 | Утверждение плана | Черновик + решение диспетчера | Утверждённый план | D4; обновление D7 `batch_stage_progress` |
| P7 | Сценарное моделирование | Базовый план, сценарий | Симуляция | D4, D5 |

**Накопители:** D1–D7 = таблицы PostgreSQL. Redis/Celery в DFD **не включать**.

## Блок 3. Архитектура и системное проектирование (UML, PlantUML / Mermaid)

### 3.1. Прецеденты использования (Use Cases)

**Диспетчер (основной пользователь UI):**

- Просмотр KPI и загрузки линий
- Просмотр очереди партий с приоритетами
- Построение сменного плана
- Просмотр Gantt и таблицы операций
- Утверждение плана
- Перепланирование после простоя
- Запуск сценариев (baseline / accelerated / emergency)
- Просмотр и подтверждение уведомлений T1/T2
- Выбор версии плана / истории

**Главный технолог / руководитель (в прототипе = диспетчер):**

- Утверждение плана для производства
- Анализ KPI и симуляций

**Модуль планирования (система):**

- Расчёт приоритета партий
- Жадное построение расписания
- Генерация уведомлений
- Архивация версий планов
- Синхронизация с мониторингом при утверждении

**Администратор комплекса:**

- Управление пользователями (`/api/v1/admin`) — вне UI planning-module
- Импорт справочников — модуль core

**Оператор / мониторинг:**

- Исполнение этапов, аварийная остановка — другой модуль, связь через общую БД

### 3.3. Диаграмма последовательностей: «Запустить автоматический расчёт расписания»

**Инициатор:** диспетчер, кнопка «Новый план».

```
Диспетчер → React App: click «Новый план»
App → nginx: POST /api/v1/plans/build
         Body: { "name": "Сменный план DD.MM.YYYY", "horizon_hours": 8 }
nginx → FastAPI: planning.build_plan()

FastAPI → PostgreSQL:
  SELECT waste_batches WHERE status IN ('accepted','queued')
  SELECT production_lines, routing_operations
  [archive_open_drafts]
  INSERT schedule_plans (draft, version_no++)
  FOR each batch (sorted by priority):
    FOR each line in route_codes:
      INSERT schedule_items (start_at, end_at, …)
  COMMIT

FastAPI → check_and_create_notifications(plan_id)
  INSERT notifications (T1, T2) при условиях
  COMMIT

FastAPI → App: 200 { plan: PlanOut, message }
App → GET /api/v1/plans?view=active
App → GET /api/v1/dashboard/kpi?plan_id={id}
App: вкладка «Расписание», отрисовка GanttChart
```

**WebSocket / Redis:** не участвуют.

## Блок 4. Макеты пользовательских интерфейсов (приложение Г)

### 4.1. Экран «Интерактивная диаграмма Ганта» (вкладка «Расписание»)

**Оси:**

- **Вертикаль:** производственные линии (`L1` — сушка/сепарация, `L2` — термообезвреживание)
- **Горизонталь:** временная шкала смены (метки ~4 деления горизонта, формат ЧЧ:ММ)

**Элементы управления (реализованы):**

| Элемент | Действие |
|---------|----------|
| «Новый план» (topbar) | `POST /plans/build` |
| «Утвердить план» | `POST /plans/{id}/approve` |
| «Перепланировать · простой L2 (8 ч)» | `POST /plans/{id}/replan` |
| PlanPicker | выбор версии, «Вся история» |
| «Обновить» | перезагрузка данных |
| ContextBar | версия, горизонт, число операций, активный утверждённый план |

**Не реализовано в прототипе:** drag-and-drop полос, «Экспорт плана», фильтры по цеху/классу на Gantt (поиск/фильтр партий — вкладка «Партии»).

**Под диаграммой:** таблица операций (партия, линия, начало, окончание, выход/потери, приоритет).

### 4.2. Экран «Оперативный дашборд планирования» (вкладка «Обзор»)

**KPI-карточки (6 шт.):**

| Метрика | Поле API |
|---------|----------|
| OEE оборудования, % | `oee_percent` |
| Выполнение плана, % | `plan_completion_percent` |
| Суммарный простой, ч | `total_idle_hours` |
| Риск хранения (число партий) | `batches_at_storage_risk` |
| Средний приоритет | `avg_priority` |
| Уведомления (новые) | `notifications_new` |

**Графики:**

- горизонтальные progress-bar загрузки по линиям L1/L2 (`line_utilization`);
- класс опасности отображается на вкладке «Партии», не на дашборде.

**Быстрые действия:** Расписание, Партии, Симуляция, Новый план.

### 4.3. Формы и модальные окна

**Реализовано:**

- **PlanPicker** (dropdown): версии плана, статус, симуляция
- **Поиск партий** (input): код / наименование
- **Симуляция:** карточки baseline / accelerated / emergency + таблица сравнения KPI
- **Уведомления:** «Подтвердить» → `PATCH /notifications/{id}/ack`

**Отдельного модального окна ручной корректировки операции нет.**

Рекомендуемый состав макета перепланирования (по API `DowntimeRequest`):

| Поле | Тип | Примечание |
|------|-----|------------|
| Партия | readonly | из контекста плана |
| Линия | select | L1 / L2 |
| Длительность простоя, ч | number | 0,5–72 |
| Причина | text | `reason` |
| Кнопки | «Применить», «Отмена» | → `POST /plans/{id}/replan` |

**Построение плана (topbar):** `name`, `horizon_hours` (в UI зафиксировано 8 ч в `App.tsx`).
