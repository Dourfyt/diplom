# UML Package Diagram — веб-модуль отчётности ECO

**Диаграмма пакетов (Package Diagram)** — структурная UML-диаграмма: деление системы на **пакеты** (логические модули, подсистемы, слои) и **зависимости** между ними (пунктирная стрелка «использует»). Отвечает на вопрос: *из каких крупных частей состоит веб-приложение и кто от кого зависит*.

Документ для раздела диплома (архитектура ПО) дополняет ER-модели (`docs/ИНФОРМАЦИОННОЕ_ОБЕСПЕЧЕНИЕ.md`), DFD, IDEF0, BPMN и UML Activity (`docs/UML_ACTIVITY_ECO.md`).

## 1. Элементы нотации

| Элемент | Обозначение | Назначение |
|---------|-------------|------------|
| **Пакет (package)** | Прямоугольник с «ушком» | Подсистема, слой, Django-приложение |
| **Зависимость** | Пунктирная стрелка `..>` | Пакет A использует пакет B (не копирует его код) |
| **Внешняя сущность** | `rectangle` / `cloud` / `database` | Пользователи, API, СУБД, смежные модули |
| **Вложенный пакет** | Пакет внутри пакета | Детализация слоя (UI и логика представления) |

**Суть для диплома:** показать структуру продукта до уровня **подсистем**: интерфейс, бизнес-логика, интеграция, данные, сквозные функции (безопасность, роли).

## 2. Рекомендации к выполнению

### Шаг 1. Выбрать уровень детализации

- **Один рисунок** — архитектура **всего** веб-модуля ECO (рекомендуется).
- Внутри слоёв — **имена реальных пакетов** (`apps.operations`, `apps.integrations`), а не абстрактные «Модуль 1».
- Не смешивать на одной диаграмме весь программный **комплекс** (учёт + планирование + ECO): соседние модули — один блок **External Systems**, данные — через **REST API**.

### Шаг 2. Слои для ECO (соответствие Django)

| Слой | Содержание в проекте |
|------|----------------------|
| **Presentation** | `templates/`, `apps/*/templates/`, `views.py`, `urls.py`, `forms.py`, статика |
| **Business** | `apps.administration`, `operations`, `monitoring`, `dashboard`, `waste`; `data_quality.py`, `reporting_export.py` |
| **Integration** | `apps.integrations`: `api_client`, `auth_api`, `remote_data`, `mixins`, `roles`, `middleware` |
| **Data** | `records.py` (DTO API), SQLite (`db.sqlite3`) — сессия и JWT |
| **Внешнее** | Пользователи; REST API + PostgreSQL `waste_complex`; модули комплекса |
| **Cross Cutting** | JWT, группы `eco_*`, `USE_REMOTE_API`, контроль доступа |

### Шаг 3. Зависимости (правило «сверху вниз»)

1. `users` → Presentation (HTTP-запросы).  
2. Presentation → Business → Integration → Data.  
3. Integration → REST API → PostgreSQL.  
4. External Systems → REST API (первичные данные не в ECO).  
5. Все основные слои → Cross Cutting (пунктиром).

**Запрещено:** стрелка Data → Presentation (обратная зависимость без обоснования).

### Шаг 4. Контрольный список

- [ ] Есть внешние участники: пользователи, API, БД.  
- [ ] ECO показан как **клиент** API, а не как владелец `waste_complex`.  
- [ ] Пакеты `apps.*` отражены в Business или Integration осмысленно.  
- [ ] Cross Cutting не дублирует весь код, а обозначает сквозные механизмы.  
- [ ] Подпись рисунка по ГОСТ 7.32 + ссылка в тексте.

### Шаг 5. Типичные ошибки

| Ошибка | Исправление |
|--------|-------------|
| Все apps в одном пакете без слоёв | Разнести по Presentation / Business / Integration |
| PostgreSQL внутри ECO | Вынести за границу модуля (внешняя БД API) |
| Стрелки «везде ко всем» | Только осмысленные зависимости по слоям |
| Подписи `GET /api/...` на пакетах | Оставить «REST API платформы» |

## 3. Описание диаграммы ECO (для таблицы в дипломе)

| Пакет / слой | Назначение |
|--------------|------------|
| **users** | Эколог, администратор, руководитель — обращение к UI |
| **Presentation Layer** | Шаблоны, статика, views, urls, forms |
| **Business Layer** | Предметная логика: администрирование, журнал, измерения, дашборд, ФККО |
| **Integration Layer** | `apps.integrations` — HTTP-клиент, аутентификация, загрузка данных с API |
| **Data Layer** | DTO (`records`), локальная SQLite (сессия, JWT) |
| **REST API / PostgreSQL** | Единое хранилище комплекса (не локальное Django) |
| **External Systems** | Модули учёта, планирования, мониторинга — поставщики данных в API |
| **Cross Cutting** | JWT, роли, политика `USE_REMOTE_API` |

## 4. Текст для раздела диплома (шаблон)

**Подпись:** Рисунок X – UML-диаграмма пакетов веб-модуля отчётности и экологического контроля ECO

**Абзац:**

> Структура программного обеспечения веб-модуля отчётности представлена UML-диаграммой пакетов (рис. X). Система декомпозирована на слои представления, предметной логики, интеграции и данных. Слой представления реализует пользовательский интерфейс на шаблонах Django и обработку HTTP-запросов во views. Предметная логика сосредоточена в приложениях `apps.administration`, `apps.operations`, `apps.monitoring`, `apps.dashboard` и `apps.waste`. Слой интеграции (`apps.integrations`) инкапсулирует обращение к REST API платформы и аутентификацию по JWT. Постоянные учётные данные хранятся во внешней СУБД PostgreSQL (`waste_complex`); локально модуль использует SQLite только для сессии и токена. Сквозной пакет объединяет механизмы безопасности и ролевого доступа. Смежные модули программного комплекса выступают внешними системами, поставляющими первичные данные в API, которые потребляет ECO.

## 5. Пример ниже (учебный)

Файл `package-example-webapp.puml` повторяет **типовую** схему из методички: Presentation → Service → Business → Data, внешние users / External Systems / Data Source / External Services, пакет Cross Cutting. Это **не** предметная область ECO; используйте для сравнения нотации или приложения.

**Отличие ECO от примера:** вместо абстрактного Service Layer — **Integration Layer** с `apps.integrations`; база данных — **вне** модуля (API + PostgreSQL).
